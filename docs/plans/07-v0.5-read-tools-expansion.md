# Plan 07: v0.5 read-tools expansion

**Status**: proposed (awaiting maintainer review)
**Phase**: post-v0.4.0 (pure tool-provider)
**Goal**: Add the high-value read-only tools identified in
`docs/research/01-tooling-expansion-2026-06.md`, plus the one piece of
infrastructure they share (an `Xml` helper). No mutating tools, no new
dependencies, no server-lifecycle changes.

## Review corrections to the research doc (2026-06-12)

Adversarial re-check of `01-tooling-expansion-2026-06.md` against two
out-of-process ADT REST clients — **ARC-1 itself** (SAPDiagnose = syntax check /
unit tests / ATC; SAPContext = reverse-dependency; SAPLint = PrettyPrint; all
over plain REST, no Eclipse) and the public `abap-adt-api` library
(`syntaxCheck`, `usageReferences`, `unitTestRun`, `atcWorklists`,
`nodeContents`, `objectStructure`, `inactiveObjects`, `revisions`,
`prettyPrinter`, `typeHierarchy`) — yields four changes:

1. **Confidence upgrades.** Every proposed REST tool is implemented by at least
   two independent out-of-process clients. The "IFile wall is a mirage for
   read-only" claim is corroborated, not just argued. Where-used / node
   structure / syntax check / unit tests / inactive / object structure:
   Med → **High**. Revisions: Low → Med (exists as `revisions` in abap-adt-api).
   The escape-hatch confirmation (research §5.2) remains the final gate before
   hard-coding, but is now expected to confirm, not discover.
2. **`check_syntax` gains an inline-source mode** (the single biggest upgrade):
   the `checkruns` body accepts an optional artifact with base64 source content,
   letting a client syntax-check **proposed** code server-side without writing
   anything. This turns the tool from "is the active version still consistent?"
   into "would my suggested edit compile?" — transient, zero mutation, and
   exactly what an AI editing loop needs.
3. **Truncation gotcha.** `AdtHttp` caps bodies at 256 KB and sets
   `truncated: true`. A truncated XML document will fail to parse. Rule for all
   parsing tools: **check `resp.truncated` before `Xml.parse`**; if truncated,
   return a clear error ("response exceeded 256 KB — narrow the scope / lower
   maxResults") instead of a parse exception.
4. **Execute-class classification.** `run_unit_tests` and `atc_check` are
   repository-read-only but **execute code server-side** (ABAP Unit does not
   guarantee DB rollback; test isolation is the test author's job). Risk profile
   = the user clicking *Run unit tests* in ADT. Ship them, but their
   descriptions must say "executes the object's tests on the backend", and they
   live in their own phase so they can be dropped without touching the rest.

## Phase A — infrastructure

### A1. `Xml.java` (~50 lines, JDK-only)

`javax.xml.parsers` ships in the JDK — D8 (no third-party deps) holds.

```java
final class Xml {
    static Document parse(String xml);                       // NS-aware, DTD/external entities disabled
    static List<Element> elements(Node ctx, String local);   // descendant elements by local name
    static String attr(Element e, String local);             // attribute by local name, any/no prefix
    static String text(Element e);                           // trimmed text content
}
```

- Namespace-agnostic by **local name** so tools never hard-code `tm:`/`adtcore:`
  prefixes (they differ across releases).
- Hardened parse: `XMLConstants.FEATURE_SECURE_PROCESSING`, no DOCTYPE/external
  entities (responses are trusted SAP backends, but it's one line).
- Later (not now): migrate `Arc1SapListTransportsTool`'s regex `parse=true` path.

### A2. `AdtHttp` Javadoc reword

The class comment still says "*POST support comes in v0.3 when where-used and
related endpoints are wired up*" — stale since v0.3 shipped POST. Reword to
describe GET+POST as current.

### A3. CONTRIBUTING: "escape-hatch-as-prototyper"

Document the standard path for new REST tools: confirm the live request/response
once with `arc1_sap_http_get`/`http_post` against a logged-in destination, then
hard-code the confirmed shape in a first-class tool. No traces, no extra tools.

## Phase C — headline reads

Shared rules: required `destination`; `maxResults` (default 50, cap 200) where
lists can explode; check `truncated` before parse (review item 3).

### C1. `arc1_sap_where_used`

```
POST /sap/bc/adt/repository/informationsystem/usageReferences?uri=<objectUri>
Content-Type: application/vnd.sap.adt.repository.usagereferences.request.v1+xml
Accept:       application/vnd.sap.adt.repository.usagereferences.result.v1+xml

<?xml version="1.0" encoding="UTF-8"?>
<usagereferences:usageReferenceRequest
    xmlns:usagereferences="http://www.sap.com/adt/ris/usageReferences">
  <usagereferences:affectedObjects/>
</usagereferences:usageReferenceRequest>
```

Optional `line`/`column` inputs append `#start=<line>,<column>` to the `uri`
query value for position-scoped where-used (member-level instead of
whole-object). Parse `referencedObjects` → `{count, truncatedList, references:
[{name, type, uri, parentUri, usageInformation}]}` capped at `maxResults`.
This is the roadmap's headline tool ("what breaks if I change this?").

### C2. `arc1_sap_package_contents`

```
POST /sap/bc/adt/repository/nodestructure
     ?parent_type=DEVC%2FK&parent_name=<PKG>&withShortDescriptions=true
(empty body)
```

Caution from review: the response is **ASX-serialized ABAP** (`asx:abap` →
`SEU_ADT_REPOSITORY_OBJ_NODE` rows: `OBJECT_TYPE`, `OBJECT_NAME`, `OBJECT_URI`,
`DESCRIPTION`, `EXPANDABLE`), not adtcore atom XML — `Xml` handles it (still
XML), but the field mapping is row-element-based, not attribute-based. Optional
`nodeId`/`parentTechName` inputs enable drilling into sub-nodes (e.g. a type
folder). Output `{count, nodes:[{name,type,uri,description,expandable}]}`.
Use case: top-down codebase exploration instead of name-guess search.

### C3. `arc1_sap_object_structure`

```
GET <objectUri>/objectstructure?version=active&withShortDescriptions=true
Accept: application/xml   (vendor type exists but plain works; confirm via escape hatch)
```

Output: nested `{name, type, uri, components:[{name, type, uri, visibility,
links…}]}`. Non-OO objects may 404 — return the backend status cleanly (the
generic error path already does). Pairs with `find_definition` /
`find_occurrences` by giving the AI member names + URIs to target.

## Phase D — quality loop (execute-class; descriptions must say so)

### D1. `arc1_sap_check_syntax`

```
POST /sap/bc/adt/checkruns?reporters=abapCheckRun
Content-Type: application/vnd.sap.adt.checkobjects+xml
Accept:       application/vnd.sap.adt.checkmessages+xml

<?xml version="1.0" encoding="UTF-8"?>
<chkrun:checkObjectList xmlns:adtcore="http://www.sap.com/adt/core"
                        xmlns:chkrun="http://www.sap.com/adt/checkrun">
  <chkrun:checkObject adtcore:uri="<mainUri>" chkrun:version="active">
    <!-- only when input.source is provided: -->
    <chkrun:artifacts>
      <chkrun:artifact chkrun:contentType="text/plain; charset=utf-8"
                       chkrun:uri="<sourceUri>">
        <chkrun:content>BASE64(source)</chkrun:content>
      </chkrun:artifact>
    </chkrun:artifacts>
  </chkrun:checkObject>
</chkrun:checkObjectList>
```

Two modes: (a) no `source` → checks the saved (active/inactive per `version`)
object; (b) `source` provided → **transient check of proposed code** (review
item 2; `java.util.Base64`, JDK). Parse `checkMessage` list →
`{messages:[{uri, line, column, type, text}]}` (line/col from the `#start=`
fragment of the message URI).

### D2. `arc1_sap_run_unit_tests`

```
POST /sap/bc/adt/abapunit/testruns
Content-Type: application/vnd.sap.adt.abapunit.testruns.config.v4+xml
Body: <aunit:runConfiguration> with adtcore objectSet referencing <objectUri>
```

Synchronous (blocks until the run finishes). Output: per test class/method
`{kind, title, alerts:[{severity, title, detail}]}` + totals. Description states
"executes the object's unit tests on the backend". Risk: long suites can run
minutes — document; do not add our own timeout (Eclipse session governs).

### D3. `arc1_sap_atc_check`

Three steps in one tool call: create worklist (`POST /sap/bc/adt/atc/worklists
?checkVariant=` — empty variant = system default, per the arc-1-lsp decompile
finding), trigger run (`POST /sap/bc/adt/atc/runs?worklistId=`), fetch findings
(`GET /sap/bc/adt/atc/worklists/<id>`). Output: findings list with priority,
check title, message, object URI. Largest tool of the set (~120 lines); last.

## Release / PR strategy

- **PR-1**: Phase A + B (infra proven on two tools, one of them Java-path).
- **PR-2**: Phase C. → tag **v0.5.0** (11 → 16 tools).
- **PR-3**: Phase D. → tag **v0.6.0** (16 → 19 tools).
- CHANGELOG `[Unreleased]` per PR; `Bundle-Version` bumped at tag time.
- **Constraint**: this repo's CI cannot compile against SAP JARs; every PR needs
  a local `./build.sh` + smoke-test pass on a machine with Eclipse/ADT + a
  logged-in destination before merge. CI still gates structure (javac parse,
  xmllint, manifest headers).

## Risks + mitigations

- **Vendor content-type drift across ADT releases** → escape-hatch confirmation
  per endpoint before hard-coding; prefer the lowest documented version; return
  raw body + status on parse-miss instead of throwing.
- **256 KB truncation breaking parse** → `truncated`-before-parse rule (review
  item 3) in every Phase C/D tool.
- **Huge where-used / package results** → `maxResults` cap + `truncatedList`
  flag in output.
- **Long-running testruns/ATC** → documented; synchronous by design (matches
  ADT UI); no client-side polling protocol to invent.
- **`IOccurrenceFinderServices` factory unknown** → resolve at build time;
  fallback is an OSGi service tracker (+10 lines); if neither works, drop B1
  without affecting the rest.
- **Tool-name regex** — all proposed names match `^[A-Za-z0-9_-]+$`.

## Self-review

- *Why not one umbrella `arc1_sap_quality` tool for D1–D3?* Same reason as
  Plan 01: narrow tools schema better for LLMs and match SAP's own
  one-purpose-per-tool convention.
- *Why is `package_contents` POST not GET?* That's the endpoint's actual shape
  (nodestructure is POST with query params + empty body) — confirmed by two
  independent clients; don't "fix" it.
- *Why ship `list_inactive` at all?* Cheapest possible proof of the `Xml`
  helper against a vendor content-type, and genuinely useful before reading
  source on systems with in-flight changes.
- *Why no `IFile` sync helper anywhere?* Research §3/§5.3: read-only clients
  never need editor-buffer semantics; `check_syntax`'s inline-source mode covers
  the "validate unsaved code" case server-side.
- *Biggest open risk?* Exact XML body acceptance per backend release. Mitigated
  by the escape-hatch confirmation step being **part of each tool's
  implementation task**, not a separate research phase.

Verdict: phased, reversible, convention-conforming. Awaiting the three
decisions above before implementation starts.
